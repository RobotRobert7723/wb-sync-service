# Технический документ `wb-sync-service`

## 1. Назначение проекта

`wb-sync-service` — серверный сервис для инкрементальной загрузки данных из Wildberries API в PostgreSQL.

Первая версия проекта предназначена для:

- самостоятельного развёртывания пользователем на Ubuntu VPS;
- работы в отдельном Docker-контейнере;
- подключения к существующей PostgreSQL;
- автоматического создания production-схемы `wb_prod`;
- запуска фоновой загрузки сразу после появления настроек в таблицах БД.

## 2. Архитектурная модель

Система состоит из одного контейнера и одного Python-процесса.

Внутри процесса работают:

- bootstrap БД;
- диспетчер воркеров;
- отдельные потоки синхронизации по каждой связке `магазин + API`;
- клиент WB API;
- слой записи в PostgreSQL;
- логирование и хранение состояния.

## 3. Основные модули

### `config.py`

Загружает runtime-конфигурацию из переменных окружения.

Поддерживает 2 режима:

- готовый `WB_SYNC_PG_DSN`;
- сборку DSN из `WB_SYNC_PG_HOST`, `WB_SYNC_PG_PORT`, `WB_SYNC_PG_DATABASE`, `WB_SYNC_PG_USER`, `WB_SYNC_PG_PASSWORD`.

По умолчанию production-схема — `wb_prod`.

### `schema.py`

Содержит SQL-описание production-схемы проекта.

Создаёт:

- `wb_accounts`
- `wb_sync_workers`
- `wb_sync_state`
- `wb_sync_runs`
- `wb_orders`
- `wb_sales`

### `db.py`

Инкапсулирует подключение к PostgreSQL и выставляет `search_path` в рабочую схему проекта.

### `repository.py`

Реализует операции чтения и записи в БД:

- чтение конфигурации воркеров;
- чтение и обновление состояния синхронизации;
- запись истории запусков;
- upsert данных `orders` и `sales`.

### `wb_api.py`

Клиент Wildberries API.

Отвечает за:

- вызов `statistics-api.wildberries.ru`;
- retry на `429/5xx`;
- account-level rate limiting;
- нормализацию дат из ответа.

### `sync_logic.py`

Инкрементальная логика синхронизации:

- определение стартового курсора;
- постраничная обработка диапазона;
- контроль продвижения курсора;
- защита от дублирования хвоста страницы.

### `worker.py`

Один worker обслуживает одну связку `account_id + api_type`.

Worker:

- получает конфиг;
- читает курсор;
- делает запрос в WB API;
- пишет данные в PostgreSQL;
- фиксирует результат в `wb_sync_state` и `wb_sync_runs`;
- ждёт следующий интервал запуска.

### `dispatcher.py`

Постоянно сравнивает желаемую конфигурацию воркеров в БД с уже запущенными потоками.

Поддерживает:

- запуск новых воркеров;
- остановку отключённых;
- hot reload при изменении конфигурации;
- изоляцию потоков по магазинам.

### `service.py`

Собирает зависимости приложения:

- `Database`
- `SyncRepository`
- `WbApiClient`
- `AccountRateLimiter`
- `Dispatcher`

### `main.py`

CLI-точка входа.

Поддерживаемые команды:

- `wb-sync init-db`
- `wb-sync run`

Команда `run` в production сначала выполняет bootstrap схемы и таблиц, затем запускает диспетчер.

## 4. Жизненный цикл запуска

### Установка

1. Пользователь запускает `install.sh`.
2. Скрипт запрашивает параметры PostgreSQL.
3. Скрипт формирует production-конфиг.
4. Скрипт собирает контейнер.
5. Скрипт запускает bootstrap БД.
6. Скрипт поднимает контейнер как постоянный сервис.

### Старт runtime

1. Контейнер запускает `wb-sync run`.
2. Сервис подключается к PostgreSQL.
3. Сервис создаёт схему `wb_prod`, если её ещё нет.
4. Сервис создаёт недостающие таблицы.
5. Сервис запускает диспетчер.
6. Диспетчер начинает опрашивать `wb_prod.wb_sync_workers`.

### Начало загрузки

1. Пользователь добавляет магазин в `wb_prod.wb_accounts`.
2. Пользователь добавляет воркеры в `wb_prod.wb_sync_workers`.
3. Диспетчер замечает новую конфигурацию.
4. Для каждой активной записи стартует worker.
5. Данные загружаются в `wb_prod.wb_orders` и `wb_prod.wb_sales`.

## 5. Схема production-данных

Production работает только в схеме `wb_prod`.

Физическая PostgreSQL может быть общей для dev и prod, но логическое разделение окружений выполняется схемами:

- `wb` — dev;
- `wb_prod` — production.

### Управляющие таблицы

`wb_prod.wb_accounts`

- магазины;
- код и имя магазина;
- флаг `enabled`;
- токен WB или ссылка на env-переменную.

`wb_prod.wb_sync_workers`

- воркеры по связке `магазин + API`;
- интервал запуска;
- lookback;
- batch limit;
- revision для hot reload.

### Таблицы состояния

`wb_prod.wb_sync_state`

- курсор синхронизации;
- heartbeat;
- last success/error;
- текущий статус worker-а.

`wb_prod.wb_sync_runs`

- история запусков;
- время старта и завершения;
- статус;
- число обработанных строк;
- ошибка, если она была.

### Целевые таблицы

`wb_prod.wb_orders`

- нормализованные данные `orders`;
- уникальность по `(account_id, record_key)`.

`wb_prod.wb_sales`

- нормализованные данные `sales`;
- уникальность по `(account_id, record_key)`.

## 6. Идемпотентность и отсутствие дублей

В первой версии система проектируется как идемпотентная.

Это обеспечивается за счёт:

- курсора `lastChangeDate`;
- tie-breaker по `record_key`;
- upsert в целевые таблицы;
- уникальных ограничений по `account_id + record_key`.

Повторная загрузка того же диапазона не должна создавать дубли. Она может повторно обновлять существующие записи, если WB прислал обновлённые значения.

## 7. Поддерживаемые API и ограничения

В первой версии поддерживаются:

- `orders`
- `sales`

Для этих методов сервис сохраняет все поля, доступные на текущий момент в официальной документации WB API.

Если WB добавляет новые поля:

- сервис не падает;
- новые поля не сохраняются автоматически;
- требуется обновление схемы и маппинга.

## 8. Обработка ошибок

Ошибки одного worker-а не останавливают весь сервис.

Поддерживаются:

- retry при временных ошибках WB API;
- запись ошибки в `wb_sync_state` и `wb_sync_runs`;
- продолжение работы остальных воркеров;
- мягкая остановка потоков при stop/reload.

## 9. Расширение проекта

Следующие версии можно развивать по направлениям:

- новые WB API;
- raw JSON-слой;
- миграционный фреймворк;
- более детальная аналитика по inserted/updated;
- внешние алерты;
- публикация готовых образов в registry.
